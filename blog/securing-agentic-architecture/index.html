01.01 · Agent identity, access, and boundaries

Identity spoofing and credential compromise

◆Critical

An attacker impersonates an agent, steals its credentials, or induces it to expose reusable secrets; automation lets the stolen identity act at machine speed.

Attack or failure path
01Spoofed input or secret theft
→
02Agent identity assumed
→
03Trusted APIs invoked
→
04Data or resources compromised
Potential impact
  • Credential takeover and persistent unauthorized access
  • Sensitive-data access or destructive production actions
  • Regulatory and forensic exposure from false attribution
Potential mitigations
  1. PreventIssue unique workload identities with short-lived, audience-bound tokens.
  2. PreventKeep secrets outside prompts and model-visible context; broker access at execution time.
  3. DetectAlert on token reuse, impossible paths, and identity/tool mismatches.
  4. RespondSupport immediate per-agent revocation and session termination.
Why Critical

Critical because a valid machine identity can directly unlock production and data-plane authority.

EvidenceAnthropic, Zero Trust for AI Agents, pp. 9–15, 27–28 · OWASP, Agentic AI: Threats and Mitigations v1.1, pp. 13–19, 30 · Supporting Claude-linked source: NIST SP 800-207, Zero Trust Architecture

Baseline qualification. This is a synthesized architectural baseline, not a publisher-assigned severity.

Context modifiers. Raise for reusable credentials or admin scopes; lower with non-exportable, narrowly scoped tokens and rapid revocation.

Architecture-review question. Can every action be tied to one non-human identity whose authority can be revoked without stopping unrelated agents?

Source detail. Anthropic, Zero Trust for AI Agents, pp. 9–15, 27–28; OWASP, Agentic AI: Threats and Mitigations v1.1, pp. 13–19, 30; supporting first-hop source reviewed from the Claude PDF: NIST SP 800-207, Zero Trust Architecture.

01.02 · Agent identity, access, and boundaries

Excessive agency and overprivileged access

◆Critical

The agent receives more tools, data, duration, or decision authority than its task requires, expanding what a single reasoning failure can do.

Attack or failure path
01Broad task request
→
02Over-scoped permissions
→
03Agent selects harmful action
→
04Large blast radius
Potential impact
  • Unauthorized changes across business or infrastructure systems
  • Sensitive-data exposure beyond task need
  • Financial, safety, and operational loss from irreversible actions
Potential mitigations
  1. PreventApply least agency: restrict tools, scope, duration, and autonomous steps.
  2. PreventUse task-specific roles and just-in-time grants instead of standing access.
  3. PreventPlace deterministic policy gates before high-impact tool calls.

Cross-cutting critical-risk summary

23 Critical baselines converge on five outcomes

01Identity takeover

Stolen or inherited authority becomes valid machine action.

02Execution & production control

Tool or code paths turn manipulated reasoning into irreversible effects.

03Exfiltration & external side effects

Read access composes with egress, messaging, or publication.

04Cross-boundary propagation

Tenants, agents, protocols, and shared integrations amplify one compromise.

05Loss of containment

Revocation, escalation, or trusted recovery fails when it matters.

The decisive design question is not “Can the model be instructed to behave?” It is “Which enforcement point still holds when it does not?”

Critical ratings are not a count of likely incidents. They mark credible paths to the high-impact outcomes defined in the methodology.

Use the five outcomes to prioritize threat modeling around the most consequential trust-boundary crossings.

Prioritized mitigation themes

Build one enforceable control spine across the agent path

01Identity plane

Unique workload identity · scoped delegation · short-lived credentials

02Context plane

Trust labels · provenance · tenant isolation · validated memory writes

03Action plane

Typed tools · policy gates · sandboxing · budgets · contextual approval

04Egress plane

Source-to-destination policy · secret isolation · output and recipient checks

05Response plane

End-to-end traces · anomaly detection · kill · revocation · trusted restore

Start hereInventory agents, identities, tools, data, protocols, and decision authority.
Then constrainReduce agency and enforce authorization at the moment of each side effect.
Then proveTrace intent to effect and rehearse granular containment and trusted recovery.

This is a cross-cutting control view, not a replacement hierarchy. Each risk remains owned within its specified family.

Prompt hardening can reduce some attacks, but it cannot replace identity, execution, network, and recovery controls.

Closing takeaways

Security architecture must own the gap between intent and effect.

  1. 01Assume external content, memory, peer messages, and tool metadata can influence reasoning.
  2. 02Keep authority smaller, shorter-lived, and more task-specific than the agent’s general capability.
  3. 03Authorize complete dataflows and action chains, not isolated tool calls.
  4. 04Design observability, revocation, and restoration before granting production autonomy.

Close on ownership: model behavior may be uncertain, but the architecture determines what the model can read, change, send, delegate, and survive.

What to take into an architecture review

  • Treat prompts, retrieved content, memory, peer messages, and tool metadata as influence—not as enforceable authorization.
  • Give each agent a unique workload identity and less authority than its general capability could use.
  • Authorize complete dataflows and action chains, not merely one tool call at a time.
  • Design traceability, granular revocation, containment, and trusted restoration before granting production autonomy.
